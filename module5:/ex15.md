# Exercise 15: Performing a CSRF Attack (Concept Notes)

## Objective

Learn how a **Cross-Site Request Forgery (CSRF)** attack works by exploiting an authenticated user's session.

---

# What is CSRF?

**Cross-Site Request Forgery (CSRF)** is an attack where an attacker tricks a **logged-in user** into performing an unwanted action.

The server believes the request is legitimate because it contains the user's valid session cookie.

---

# Lab Scenario

The vulnerable application is a simple **bank transfer** page.

The user is already logged in.

Example:

```text
Balance : 1000€
```

Transfer page:

```text
Account Number : 12345
Amount         : 500€
```

When the user clicks **Transfer**, money is transferred.

---

# Step 1: Create a New User

Create a new user account in bWAPP.

**Why?**

This user acts as the **victim** in the CSRF attack.

---

# Step 2: Login with the New User

Log in using the newly created account.

Ensure the **Security Level = Low**.

---

# Step 3: Open the CSRF Module

Choose:

```
Cross Site Request Forgery (Transfer Amount)
```

Click **Hack**.

---

# Step 4: Observe the Transfer Request

Click **Transfer**.

Notice that the browser sends a request similar to:

```text
transfer.php?account=12345&amount=500&action=transfer
```

The transfer details are visible in the URL.

---

# Why is This a Problem?

The application trusts whatever values are received.

An attacker can modify values such as:

- Account Number
- Transfer Amount

and send the modified request to the victim.

---

# Step 5: Copy the Transfer URL

Save the transfer URL.

**Why?**

An attacker can modify this request and use it later in a fake web page.

---

# Step 6: View Page Source

Open:

```
View Page Source
```

Locate the HTML form used for the transfer.

Copy the form into a new HTML file.

---

# Why Copy the Form?

Instead of creating a new form from scratch,

the attacker simply copies the original transfer form and modifies the values.

Example:

Original:

```text
Account : 12345
Amount  : 500€
```

Modified:

```text
Account : 99999
Amount  : 500€
```

---

# Step 7: Save as HTML

Example:

```text
attack.html
```

This page becomes the attacker's fake web page.

---

# Step 8: Victim Opens the Page

The attacker tricks the victim into opening the HTML page.

Examples:

- Phishing email
- Fake website
- Malicious blog
- Social engineering

The victim clicks **Transfer**.

---

# What Happens?

The browser automatically sends:

- Transfer request
- Session cookie

Because the victim is already logged in.

The server receives:

```text
Valid Session Cookie
+
Transfer Request
```

The server believes the request came from the legitimate user.

---

# Result

Money is transferred without the victim realizing it.

Example:

```text
Before

Balance = 1000€
```

↓

```text
After

Balance = 500€
```

The money has been transferred to the attacker's account.

---

# Complete Attack Flow

```text
Victim Logs In
        ↓
Session Cookie Created
        ↓
Attacker Copies Transfer Form
        ↓
Changes Account Number
        ↓
Creates Fake HTML Page
        ↓
Victim Opens Page
        ↓
Victim Clicks Transfer
        ↓
Browser Automatically Sends Session Cookie
        ↓
Server Thinks Request Is Legitimate
        ↓
Money Transferred
```

---

# Why Does the Attack Work?

The application:

- Uses the user's session cookie for authentication.
- Does **not** verify whether the request came from its own website.
- Does **not** use a CSRF token.

Therefore, forged requests are accepted.

---

# How to Prevent CSRF?

- Use **CSRF Tokens**.
- Verify the **Origin** or **Referer** header.
- Require re-authentication for sensitive actions.
- Use `SameSite` cookies where appropriate.

---

# Key Concepts

| Term | Description |
|------|-------------|
| CSRF | Tricks a logged-in user into performing unwanted actions. |
| Session Cookie | Identifies the authenticated user. |
| Victim | A legitimate logged-in user. |
| Attacker | Creates a fake page containing a forged request. |
| CSRF Token | A unique token used to prevent forged requests. |

---

# Exam Points

- Victim **must already be logged in**.
- Browser automatically sends the session cookie.
- Attacker modifies the transfer request.
- A fake HTML page is used to trick the victim.
- The server accepts the request because no CSRF protection exists.

---

# One-Line Summary

**This lab demonstrates how an attacker can copy a legitimate transfer form, modify its values, place it in a fake HTML page, and trick a logged-in user into submitting it. Since the browser automatically includes the user's session cookie, the server processes the forged request as if it came from the legitimate user.**
